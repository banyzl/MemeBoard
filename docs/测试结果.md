## 自动粘贴问题的实际记录

- 用户已在系统权限页面开启 Helper，独立运行 `doctor` 能报告 Accessibility 和 PostEvent 可用。
- 初版 Helper 从 Rime 启动时记录权限不足，图片仍成功复制，逗号没有提交图片名称文字。
- 初版 Helper 从 Raycast 启动时未报告权限不足，但 QQ 未显示图片；同一剪贴板手动 ⌘V 可插图。后续记录到实际系统前台为 `com.openai.codex`，所以这次观察不能判为 QQ 自动粘贴失败。
- 已改进 Helper：同时检查 Accessibility 与 PostEvent，检查前台 PID、剪贴板版本，保留 composition 清除等待，发送完整 Command/V 按下释放序列，并在退出前留出事件处理时间。用户已开启 Helper 与鼠须管权限。
- 真实自动化测试的日志随后确认 `target_app com.openai.codex`；自动化可向 QQ 控件输入，但未切换系统前台。因此改由用户保持 QQ 前台完成两条链路的实际验收。用户已分别确认两条链路均出现图片；最终通过依据为用户实际界面反馈，而非 Helper 的返回值。
- 日志只记录事件、UUID 及诊断所需的应用 bundle ID，不记录聊天内容。

## MVP 验收结论

项目要求的两条完整链路已实际通过：

1. Raycast 导入图片 → 命名 → 搜索 → Enter → QQ 输入框出现图片。
2. 导入后自动生成 Rime 索引 → QQ 输入 mmwy → 图片 Prompt → 逗号 → QQ 输入框出现图片。

导入、命名、Grid 与搜索由自动化工具实际操作并观察；两条自动粘贴链路的最终插图由用户在 QQ 前台实际操作并确认。用户确认前已完成生产 Helper 与鼠须管的系统权限授权。

## 0.1.1：TIFF 格式排查与修复

- 未发现项目设置或修改系统截图格式；代码不存在截图/剪贴板监听器。
- 旧 Helper 确实主动写入 PNG 与 TIFF 两种源格式；已移除显式 TIFF，原始项仅含 `public.png`。
- 旧诊断程序直接写 NSImage，会产生 TIFF 源数据；已改为显式 PNG 项。
- 独立对照实验：只写 PNG 后，`pasteboardItems.first.types` 仍为 PNG，
  但 `NSPasteboard.types` 自动额外列出 PNG/TIFF 兼容格式；这是系统提供的转换。
- 原生回归测试覆盖四种输入格式归一为 PNG、原始项仅含 PNG 且不含文件 URL、
  AppKit 仍能读取为图片、无效输入保留既有测试剪贴板。
- 没有改写用户的旧 Raycast 剪贴板历史，没有清空或重写用户当前剪贴板。
- 打开 Raycast 后普通截图变为 TIFF 的全局现象，尚不能归因为 MemeBoard；
  Raycast 官方对 TIFF 历史图片提供 **Paste as PNG** 操作。

用户后续复测确认：MemeBoard 复制已正常；与 MemeBoard 无关的普通截图经 Raycast 内置剪贴板仍出现 TIFF。项目侧的源格式修复已生效，未将 Raycast 普通截图的全局格式选择问题标记为已解决。
